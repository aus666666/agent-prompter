# 系统提示词修订与审计

仅在用户提供现有提示词，或要求扩展、重构、评审时读取。目标是改变必要行为，同时证明用户原有要求没有被静默丢失。

## 一、建立轻量需求台账

修订前先提取需求。复杂任务可使用以下字段，简单任务可在内部完成核对：

| 字段 | 含义 |
| --- | --- |
| ID | 用于追踪的稳定编号 |
| 来源 | 用户明确要求、原提示词、平台事实、保守默认或待确认 |
| 强度 | 硬约束、条件规则、默认偏好或示例 |
| 原要求 | 尽量保持原意的简短记录 |
| 处置 | 保留、澄清、拆分、替换、删除或待确认 |
| 目标位置 | 新提示词中的落实位置 |
| 验证方式 | 能观察到该要求是否生效的场景 |

用户要求逐字保留的文本必须逐字保留。其他内容默认保留语义，不要求保留所有原句。替换或删除用户硬约束必须说明原因；未获授权时不得把它静默当作“优化”。

## 二、诊断真实缺陷

只报告会改变行为或可维护性的缺陷。每个问题用“原文证据 → 行为风险 → 最小修复方向”描述。

重点检查：

- 目标不可观察，或使用“永远正确”“做到最好”等无法验证的承诺。
- 关键能力缺少触发条件、动作、结果检查或失败路径。
- 重复、矛盾、循环、永不停止或无法到达的流程。
- 工具、权限、知识来源或连接状态与真实配置不符。
- 将未确认的评分阈值、审批规则、来源优先级或合规口径包装成“临时默认”。
- 无条件流程造成过度调用、过度追问或不必要拒答。
- 示例、占位符或参考模板内容意外升级为硬规则。
- 同一规则散落在多处，形成多个可能漂移的权威版本。
- 输出格式只适合示例，无法覆盖真实输入规模或异常场景。

不要用装饰性评分代替具体证据和影响。用户只要求评审时，按严重程度排列发现，并遵守其是否允许替代文案的边界。

## 三、裁决冲突

1. 先确认规则是否作用于相同条件。条件不同的规则应拆成分支，不是假冲突。
2. 同一权威层级中，硬约束优先于默认偏好；范围更窄的条件规则优先于一般规则。
3. 规范正文优先于示例；示例默认只校准风格或形态。
4. 不采用“后出现的规则自动获胜”。
5. 能按真实能力、事实依据和授权边界保守解决时，给出统一版本并记录处置。
6. 无法裁决且会改变核心业务行为时再追问；若用户要求先给草稿，使用待确认标记而不是冒险选择。

## 四、按操作保真修订

### 扩展

- 原有行为默认不变，新能力只在对应触发条件下启用。
- 不因新增模块强迫所有请求走新流程。
- 新规则与旧规则冲突时先处理冲突，不把旧要求悄悄放宽。

### 重构

- 先锁定不可变项，再重排结构和去重。
- 保留平台标记、工具名、变量名、固定术语，以及外部解析依赖的标题或字段。
- 每条规则只保留一个权威位置；需要复用时引用其原则，不复制出新版本。
- 将稳定行为核心、易变配置和输出示例分开。
- 区分“预期行为变化”和“只改变结构或表达”。

### 评审

- 只输出发现、证据、影响和用户允许范围内的修改方向。
- 用户禁止重写或替代片段时，不输出任何可复制修订文案。
- 不因为看出问题就擅自扩大交付范围。

## 五、变更追踪

复杂扩展、重构或专业交付时提供变更映射。至少覆盖用户硬约束和有意改变的行为：

| 需求 ID | 原要求 | 处置 | 新位置 | 行为是否改变 | 验证方式 |
| --- | --- | --- | --- | --- | --- |

简单修改不强制展示完整表格，但仍需内部逐项核对。用户指定了对照表字段时，严格遵循其格式。

## 六、就绪状态

- 草稿：仍有关键假设、未解决冲突或阻塞性占位符。
- 配置就绪：行为规则完整，但工具、知识库、变量、权限或平台绑定仍待完成。
- 部署就绪：关键绑定真实有效，无阻塞占位符，冲突已经解决，并通过与需求映射的行为验收。

只根据当前证据声明状态。没有实际执行测试时，不能声称已经验收通过。
