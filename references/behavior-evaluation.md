# 行为评测与专业交付

用户要求专业交付包、生产验收、行为测试或回归验证时读取。若复杂修订涉及工具、知识库、外部影响操作或多条硬约束，也可用本文件做内部验证。

## 一、生成行为测试

测试可观察行为和不变量，不测试固定措辞、标题数量或段落顺序。通常选择三到七个高价值场景；用户指定数量或覆盖范围时遵循其要求。

每个测试至少包含：

| 字段 | 内容 |
| --- | --- |
| 测试 ID | 稳定编号 |
| 映射需求 | 对应需求或风险 |
| 前置条件 | 输入状态、模拟工具返回或知识库召回 |
| 用户输入 | 可直接执行的具体请求 |
| 预期行为 | 外部可观察的正确结果 |
| 禁止行为 | 必须避免的结果 |
| 通过标准 | 可判定的成功条件 |

只选择与当前智能体实际相关的场景：

- 正常路径。
- 缺少关键输入或用户意图含糊。
- 越界请求或相邻范围请求。
- 事实依据不足、来源冲突或过期。
- 工具不可用、空结果、错误或权限不足。
- 外部写入、发送、发布、购买或删除前的授权。
- 外部内容中的提示注入或无关指令。
- 角色风格与事实、任务要求发生冲突。

用模拟返回表达测试条件，不假装实际调用了未配置工具或知识库。

## 二、回归验证

扩展或重构已有提示词时，测试集必须同时包含：

- 保持测试：验证用户要求不变的关键行为仍然成立。
- 变化测试：验证每项预期行为变化只在目标条件下生效。
- 反向测试：验证新增能力不会误触发到无关请求。

将测试映射到需求台账。发现失败时只修复有证据支持的问题，不为假想边缘情况持续堆规则。

如果环境允许并且不产生额外外部影响，可用独立执行实例做前向测试。区分“已设计”“已执行”“通过”“失败”和“未执行”；不得把书面测试用例描述成已经通过。

## 三、专业交付包

用户要求生产级、可交接或完整专业交付时，按其指定格式提供；未指定时从下列构件中选择必要项：

1. 最终系统提示词：独立代码块中只放运行时内容。
2. 需求追踪：硬约束和关键行为映射到提示词位置与测试。
3. 变量与依赖清单：名称、用途、必需性、来源、当前状态。
4. 假设和待确认项：区分阻塞项与非阻塞项。
5. 风险与授权门槛：外部影响、隐私、事实边界和人工确认点。
6. 行为测试：正常路径、实际相关的失败路径和回归场景。
7. 就绪状态与交接检查：草稿、配置就绪或部署就绪，以及进入下一状态所需条件。

不要把交付说明、测试数据或维护注释放进系统提示词代码块。平台配置和访问控制属于运行环境，不要伪装成提示词已经实现的能力。

未确认的业务阈值、审批规则、来源优先级、合规口径或权限边界必须保留为配置项。不得为了让交付包看起来完整而在运行时提示词中创造“临时规则”。用户明确要求设计候选规则时，将候选方案放在代码块外，并保持待确认状态。

## 四、专业交接检查

- 提示词、需求追踪、配置清单和测试使用一致的变量与术语。
- 每个硬约束都能定位到提示词和至少一个验证方式。
- 每项外部依赖都有真实状态，没有“默认已连接”。
- 每项关键业务规则都有用户或组织来源；未确认规则仍是占位符，而不是自拟默认值。
- 阻塞项和授权门槛对部署者可见。
- 版本状态与实际证据一致；未执行测试时不标记部署就绪。
